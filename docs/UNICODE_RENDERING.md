# TermExplorer Unicode & Text Fidelity Architecture

## Overview

Text editing and filesystem navigation in international development environments require comprehensive Unicode compliance. TermExplorer operates at the grapheme-cluster level rather than raw ASCII bytes or isolated UTF-8 codepoints.

---

## 1. Grapheme Cluster Boundary Navigation (GAP-05)

### The Multi-Codepoint Problem
In standard Unicode, user-perceived characters ("graphemes") frequently consist of multiple Unicode codepoints:
- **Flag Emojis**: Composed of two Regional Indicator symbols (e.g. `🇮🇳` is `U+1F1EE` + `U+1F1F3`).
- **Skin Tone Modifiers**: Composed of a base emoji + modifier (e.g. `👍🏽` is `U+1F44D` + `U+1F3FD`).
- **Zero-Width Joiner (ZWJ) Sequences**: Multiple symbols joined by `U+200D` (e.g. `👨‍💻` is Man + ZWJ + Laptop).
- **Combining Diacritics**: Base letter + combining mark (e.g. `é` is `e` + `U+0301`).

If a text editor navigates or deletes using `char` or byte offsets, it splits these sequences, resulting in corrupted orphan codepoints, missing skin tones, or broken flag symbols.

### Grapheme-Safe Editing (`src/editor/buffer.rs`)
TermExplorer enforces grapheme cluster boundaries using `unicode_segmentation::UnicodeSegmentation`:
1. **Cursor Columns**: `buffer.cursor.col` indexes grapheme clusters, never raw bytes or isolated codepoints.
2. **Horizontal Navigation (`move_left`, `move_right`)**: Steps across whole grapheme clusters in a single stroke.
3. **Backspace (`backspace`)**: Removes the entire preceding grapheme cluster as an indivisible unit.
4. **Delete (`delete_char`)**: Removes the entire grapheme cluster under the cursor.
5. **Selection & Cut/Paste**: Visual selections operate strictly on grapheme cluster boundaries.

## 2. UTF-8 BOM Preservation (GAP-07)

Many tools and editors on Windows (Visual Studio, Notepad, PowerShell) write a UTF-8 Byte Order Mark (`0xEF, 0xBB, 0xBF`) at the start of text files.

- **Load Protocol**: When loading via `Buffer::from_file`, TermExplorer detects the three-byte BOM signature, strips it from internal editor memory to prevent syntax parsing issues, and flags `encoding: FileEncoding::Utf8Bom`.
- **Save Protocol**: When writing via `save_force()`, TermExplorer prepends `0xEF, 0xBB, 0xBF` back to the file stream before atomic persistence.
- **Fidelity Guarantee**: Files generated by Windows environments retain their exact byte signatures and BOM metadata when edited within TermExplorer.

---

## 3. Fallback Encoding Detection (Latin-1 / ISO-8859-1)

When opening legacy configuration files, logs, or source code that contain non-UTF-8 byte sequences:
1. TermExplorer attempts standard UTF-8 parsing.
2. If invalid UTF-8 bytes are encountered, it automatically falls back to **ISO-8859-1 (Latin-1)** decoding, mapping every byte `0x00..=0xFF` directly to its corresponding Unicode codepoint (`c as char`).
3. Sets `encoding: FileEncoding::Latin1`.
4. Surfaces the active encoding in the editor header:
   ```text
   ✏ filename.txt [Latin-1 | LF]
   ```
5. On save, if all characters are `<= 255`, TermExplorer writes them back as single-byte Latin-1 characters, preventing unwanted re-encoding.
